## Architecture and current features

- Backend: Next route handlers; no separately running backend or job worker found.
- Persistence: Prisma 6.19.3 with PostgreSQL. Initial and authentication-rate-limit migrations exist. Models: User, Account, Session, VerificationToken, AuthRateLimit, Wallet, PaperAccount, PaperPosition, PaperOrder, PaperTrade, Strategy, Watchlist, WatchlistItem, AuditLog. Monetary paper-trading fields use PostgreSQL Decimal. Schema presence does not mean a working trading feature.
- Authentication: Auth.js v5 beta, credentials provider, Prisma adapter, JWT sessions; session user IDs derive from token subjects. Passwords use salted scrypt and timing-safe verification. Login and registration have database-backed attempt limits. No active OAuth provider, password recovery, email verification, or MFA.
- Routes: `/` landing link, `/auth/login` registration/sign-in form, `/dashboard` protected server layout with client dashboard. Dashboard includes responsive sidebar, virtual NPR/USDT balances, balance reset confirmation, sample market search/selection, illustrative chart/timeframes/crosshair, animation pause, and buy/sell value preview. Preview sends no orders.
- Existing APIs: `GET/POST /api/auth/[...nextauth]` (Auth.js), `POST /api/auth/register`, `GET /api/wallet`, `POST /api/wallet/reset`. Wallet routes scope reads/writes to authenticated user ID.
- Data: active dashboard has fixed illustrative BTC/ETH/SOL/NEPSE prices and mathematically generated SVG history. Static `index.html`, `app.js`, `chart.js` and `trading-dashboard/` are independent prototypes with generated candles. No live provider, source credentials, quote API, historical-bar store, active socket, or exchange/broker execution integration was found. Existing demo labels must remain explicit; these prices must never drive an execution engine.
- `market_data_pipeline.ts`: disconnected in-memory candle aggregation, depth book and dispatch classes. `oms_risk_engine.ts`: disconnected in-memory risk/FSM classes. `security_middleware.ts`: disconnected signing and token-bucket classes. None is imported by `src`. Do not treat their comments claiming production readiness as verified functionality.
- `src/components/dashboard/` includes unused placeholder components in addition to components used by the dashboard. Root README documents the two application forms. Vercel runs Prisma migrations before the build.

## Problems, security concerns, and gaps

1. No functioning order lifecycle, paper fills, portfolio accounting, fees, journal, alerts, screener, or backtesting. Buying power and P/L cannot honestly be calculated from the independent demo wallets alone.
2. Wallet and PaperAccount balances are separate models/currencies. Choose one authoritative paper ledger per currency before execution. Never add NPR, USD, and USDT balances without an explicit FX source and valuation policy.
3. Reset API originally has no origin validation, mutation limit, or audit event. It must stay limited to virtual Wallet balances and must not silently reset future position/account ledgers.
4. Root has no `.env*` files. Database connectivity and authenticated runtime behavior have not been established. Production requires DATABASE_URL, AUTH_SECRET, and canonical AUTH_URL. Nested checkout environment files are not root configuration.
5. IP limits rely on x-forwarded-for; production must use a trusted proxy that replaces inbound spoofed forwarding headers. Rate-limit rows need an expiry cleanup policy. Registration duplicate response can disclose account existence. Auth failures from database outages need operational error handling.
6. No application-wide CSP/security-header policy, session revocation strategy, or authorization role policy found. Existing SQL access uses Prisma rather than user-built raw SQL. No frontend broker secret was found in inspected source. OAuth token columns would need a storage/encryption policy before providers are enabled. Development Prisma query logging should be reviewed for sensitive data.
7. Disconnected risk code uses JavaScript numbers, lacks comprehensive positive/finite quantity and leverage checks, and stores idempotency only in memory. Reduce-only validation does not establish opposing direction. State transitions mutate an object, not an atomic database row. Fill validation must reject overfills/nonpositive fills and enforce decimal precision.
8. Disconnected HMAC validator can throw for unequal signature lengths; malformed receive windows can bypass expiry comparisons. A timestamp window alone does not prevent replay within the window. These modules are not active endpoint protection.
9. Data pipeline has no provider ingestion/reconnect/persistence wiring. Optional previous-sequence checks do not cover every feed's first/last sequence rules. Validate ticks, ordering, duplicates, stale quotes, gaps, and instrument identity before reuse.
10. Root TypeScript glob includes the nested checkout; ESLint can traverse its generated files. Isolate root verification from the separate checkout. Existing build succeeded; installed direct dependencies resolve. No new library is needed for the first increment. Charting/provider dependencies should only be selected when integration requirements are known.
11. Existing previews use floating-point display arithmetic; financial execution must use decimal arithmetic and explicit tick/lot rounding. Default leverageLimit=50 is a schema default, not a validated permission to enable leverage.
12. Root metadata remains scaffold text. Chart history and timeframe changes are illustrative, not actual historical bars or technical indicators. Dark styling exists, but no complete user-selectable light theme.

## Recommended phases and affected modules

1. **Security and persisted watchlists (first increment):** preserve credentials and virtual wallets; add shared origin validation, reset throttling and transactional reset audit; activate existing Watchlist tables with authenticated owner-scoped CRUD, validation, limits, multiple lists, filtering, and add/remove UI. No new schema needed. Files: `src/lib/request-security.ts`, `src/lib/watchlists.ts`, wallet reset route, `src/app/api/watchlists/route.ts`, new dashboard watchlist component, dashboard page/CSS, tests and setup docs.
2. **Trustworthy market data:** choose a permitted provider and supported instruments; implement server-side adapters, symbol metadata/search, timestamped quotes and OHLCV history, freshness/error states and subscription/reconnect handling. Do not fall back to sample prices on failure. Replace illustrative market displays only once this is working. Files: new `src/lib/market-data/`, market API routes, MarketChart, dashboard. Adapt pipeline classes only after tests. Provider configuration is required.
3. **Paper ledger and order service:** reconcile account currencies; implement decimal risk checks and serializable transactional cash/position/fill/fee updates, database idempotency, cancellations, audit events and durable pending-order evaluation. Begin with unleveraged market/limit orders supported by actual quote data; add stop and bracket types only with reliable trigger processing. Require a server-generated expiring preview and explicit confirmation before submission. Migrate PaperAccount/Order/Trade as needed, including unique client IDs, journal fields and risk settings. Never enable real-money trading.
4. **Dashboard, charts and portfolio:** authoritative cash/buying power/daily and total P/L, exposure, recent fills, positions, market overview and gainers/losers; interactive OHLCV candles, timeframe/symbol/fullscreen/zoom/pan/crosshair/volume; tested SMA, EMA, RSI, MACD, Bollinger, ATR and session-defined VWAP. Add portfolio page and timestamped equity snapshots; migration for equity history. Preserve navigation and responsive shell; add theme toggle and consistent empty/loading/error states.
5. **Risk and journal:** user risk-per-trade, sizing/stop calculator, maximum position/daily loss/exposure rules enforced on server, ledger-backed performance, trade notes/strategy and metrics. Store daily reference equity and make timezone boundaries explicit. Files: risk service, risk settings API/UI, journal API/page, schema migrations.
6. **Alerts and screener:** persisted alert definitions, deduplicated events, background worker and in-app notifications; screen only instruments with real required data. Price/move/volume/indicator alerts and screener price/change/volume/relative-volume/volatility/RSI/MA/high-low filters. Migrations for alerts/events; worker deployment required.
7. **Backtesting:** historical data service, reproducible rules and fees/slippage, next-bar execution for close-derived signals, warmup periods and no future-bar access. Date/timeframe/symbol/sizing/SL/TP/capital controls; equity/trades/return/win-rate/profit-factor/drawdown/Sharpe results with explicit assumptions. Add persisted runs and dataset provenance.
8. **Release hardening:** integration tests against an isolated PostgreSQL database, multi-user ownership and concurrency tests, provider outage/staleness tests, browser/accessibility checks, security headers, structured error handling, secrets rotation, backup/restore, monitoring and deployment verification. Any future broker integration is a separate explicitly authorized project phase.
